# 記事配信前セルフチェックツール 構想まとめ

## 1. 背景・目的

外注メンバーがニュースメディア配信前の記事チェック(校正・画像挿入)を行う際、レギュレーション違反や設定漏れを **自分自身で事前に検出** できるツールを導入したい。

これまでに発生したミスの傾向:

- 削除しなければいけない文言が残っていた
- タイトルが時勢に合わない(修正対象だった)
- 関連記事に余計な文字列が入っていた
- 関連記事がその記事に対して合っていない(CTRが高まらなそう)
- 画像挿入箇所の漏れ

これらを自動 / 半自動で検出し、納品前のセルフチェックを標準化することが目的。

---

## 2. 前提条件

| 項目 | 内容 |
|---|---|
| 外注のPC環境 | Windowsユーザーが多数。PCが古い人もおり、Chromeが最新でない場合がある |
| 管理側のPC環境 | Mac |
| コスト | 無料運用が前提 |
| 認証 | WordPress管理画面はログイン必須 + Basic認証あり |
| チェック方式 | できる限り自動判定したい(目視チェックリストは最小限) |
| 納品時の証跡 | 不要(外注の自己申告でOK) |

---

## 3. ツール形態:ブックマークレット方式

### 採用理由

- ブラウザのバージョン依存が少ない(古いChromeでも動作)
- インストール不要
- WordPress管理画面のログイン・Basic認証はブラウザが既に通しているので、追加認証不要
- WindowsでもMacでも同じ仕組みで動く
- 管理側でルールを更新すれば全員に即時反映可能

### 動作フロー

1. 外注がWordPress管理画面で記事のプレビューを表示
2. ブラウザのブックマークバーから「記事チェック」をクリック
3. プレビュー画面上にチェック結果パネルがオーバーレイ表示される
4. 修正が必要な箇所を確認 → WordPressに戻って修正

### 技術構成

```
[外注のブラウザ]
    ↓ ブックマークレットをクリック
[ローダー (短いJSスニペット)]
    ↓ 外部JSを読み込み
[チェックロジック本体 (checker.js)]
    ↑ 管理側がここを更新するだけで全員に反映
[ホスティング:Cloudflare Pages / GitHub Pages 等の無料枠]
```

外注側のブックマーク登録は初回のみ。以降のルール更新で再登録は不要。

---

## 4. チェック項目(実装予定)

### 自動判定で確実に拾えるもの

| # | 項目 | 内容 |
|---|---|---|
| 1 | 残置文言検出 | NGワードリストとの照合(「※情報は◯月号掲載時のものです」「撮影／〇〇 スタイリスト／〇〇」など、配信時に削除すべき文言) |
| 2 | 引用元名の残存 | 本文中に掲載元独自の固有名詞が残っていないか |
| 3 | 関連リンク数 | 規定数(固定)と一致しているか |
| 4 | 関連リンクURL | 正しいドメインか、リンク切れの可能性がないか |
| 5 | 関連リンクタイトル | 規定の記号(▶)が頭についているか |
| 6 | 媒体とドメインの整合性 | タイトル末尾の媒体名と関連リンクのドメインが一致しているか自動照合(下記マッピング参照) |
| 7 | 画像設定漏れ | 段落ごとに画像ファイルがセットされているか(第1段落だけ未設定など段落単位で検出) |
| 8 | 段落構造 | 段落見出し・本文・画像のセットが揃っているか |
| 9 | HTML異常 | 空タグ、不要なインラインstyle、非推奨タグの残存 |

### 検出して目視判断を促すもの

| # | 項目 | 内容 |
|---|---|---|
| 10 | タイトルの時勢ワード | 「最新」「今年」「先日」「5月」「春」など、配信日とズレる可能性がある表現をハイライト |
| 11 | 本文の時勢ワード | 同上、本文側もハイライト |
| 12 | 関連記事の妥当性 | 本文キーワードと関連記事タイトルを並べて表示し、目視で判断を促す |

## 5. 対象媒体とドメイン対応表

タイトル末尾の媒体名と関連リンクのドメインの整合性チェックに使用する。

| 媒体名 | ドメイン |
|---|---|
| JJ | jj-jj.net |
| VERY | veryweb.jp |
| CLASSY. | classy-online.jp |
| STORY | storyweb.jp |
| bis | bisweb.jp |
| Mart | mart-magazine.com |
| 美ST | be-story.jp |

### 判定ロジック

```
1. 記事タイトル末尾の「｜媒体名」から媒体を特定
2. 上記マッピング表から正解ドメインを取得
3. 関連リンクのURLを1件ずつチェック
4. ドメインが一致しないリンクがあれば「要修正」として該当URLを表示
```

### 判定例

| タイトル末尾 | 期待ドメイン | 関連リンクURL | 判定 |
|---|---|---|---|
| ｜STORY | storyweb.jp | https://storyweb.jp/fashion/723082/ | OK |
| ｜STORY | storyweb.jp | https://veryweb.jp/articles/xxx | 要修正(媒体違い) |
| ｜VERY | veryweb.jp | https://veryweb.jp/articles/xxx | OK |

新媒体が追加された場合は、このマッピング表を更新するだけで対応可能。

## 6. 仕組み的にできること / できないこと

### できること

- WordPressプレビュー画面のDOMから情報を直接読み取り、構造化されたチェックが可能
- タイトル、段落見出し、本文、画像有無、関連リンクのタイトル・URLを段落単位で取得
- 媒体名と関連リンクドメインの整合性を自動判定
- ルール(NGワード、媒体マッピング等)の追加・変更を管理側で完結(外注の再設定不要)
- 完全にブラウザ内で処理が完結(記事内容が外部サーバーに送信されない)
- 操作は「プレビュー開く → ブックマーククリック」の2ステップ

### できないこと

- 「関連記事が本文にCTR的に合っているか」の最終判断は自動化できない(目視判断を促す表示までが限界)
- 時勢ワードの自動修正は不可(検出と警告のみ。配信日との照合で「要確認」とハイライトする)
- 画像の内容が本文に合っているかの判断は不可(画像の有無のみ判定)
- 意味的に自然な日本語かどうかの校正は不可

> 上記の「できないこと」のうち時勢判断や関連記事の妥当性については、将来的にAI APIを組み込めば自動化可能。ただし有料運用になるため、まずは無料のルールベースで運用開始する。

## 7. 運用イメージ

### 外注側の作業フロー

1. WordPressで記事を編集
2. プレビューを開く
3. ブックマークバーの「記事チェック」をクリック
4. オーバーレイで結果を確認
5. 「要修正」が0件になるまで修正
6. 「要確認」項目は目視で判断
7. 問題なければ納品

### 管理側の作業フロー

- 新しいミス傾向が発見されたら、NGワードリストや媒体マッピングをJSON / JSファイルで更新
- 新媒体が追加されたら、マッピング表に1行追記
- GitHub等にpushすればホスティング先に自動反映 → 外注全員に即時反映

---

## 8. 残課題・要確認事項

実装に進む前に、以下の確認が必要:

1. **プレビュー画面のHTML構造の確認**
   - DOM構造を確認することで、確実に動くセレクタを記述できる
   - 開発者ツールでの確認 or ページソースの共有が必要

2. **関連リンクの規定数**
   - スクリーンショット例では5個。固定値の正確な数を確認

3. **削除対象文言の具体例リスト**
   - 過去に削除し忘れた具体的な文言を洗い出してNGワードリスト化
   - 例:「※情報は2026年5月号掲載時のものです」「撮影／〇〇 スタイリスト／〇〇」など

4. **媒体名表記ゆれの有無**
   - タイトル末尾の媒体名は「｜STORY」固定か、「| STORY」「|STORY」など揺れがあるか
   - 全媒体について同一フォーマットになっているか確認

5. **関連リンクは常に同一媒体のみか**
   - 例外的に他媒体のリンクを混ぜるケースがあるか
   - ある場合は「許容パターン」を別途定義する必要あり

6. **ホスティング先の決定**
   - Cloudflare Pages / GitHub Pages のどちらにするか
   - チェックロジックのコード管理方法(GitHubリポジトリ等)
